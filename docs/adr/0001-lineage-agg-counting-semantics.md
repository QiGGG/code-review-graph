# 0001 — lineage 聚合采用函数身份去重 + 函数行数求和口径

`lineage-agg` 统计「作用域（单文件/文件夹）内所有函数的血缘覆盖代码量」时，决定按**函数节点身份（`qualified_name`）去重**、把每个纳入函数按 `行尾 - 行首 + 1` 求和作为总行数；不做物理行并集去重，也不为嵌套函数身份局限单独修复建图层。

这个口径与既有单函数 `lineage` 完全一致（`lineage.py::compute_scale` 即按函数行数求和、`_FUNCTION_KINDS` 只含 Function/Test），因此聚合结果与单函数结果在同一计量单位下可比。血缘覆盖允许越出作用域延伸至全仓任意文件，作用域只决定「哪些函数入根」。

选择不采用的两个替代方案及原因：

- **物理行并集去重**（同一行被多个函数/嵌套覆盖只算一次）：语义更"精确"，但与单函数口径断裂，且需引入行区间合并的额外算法，会让"覆盖行数"失去与既有功能的可比性。
- **排除函数体内嵌套 def / 修 parser 让 qn 含外层函数**：前者会误伤 Java 匿名/局部类方法（其节点物理上嵌在外层方法体内但语义独立、且通常由框架调用，无法经外层血缘到达）；后者需改建图 schema 并全仓重图，波及 review/visualize/impact 等所有下游，属独立架构变更。

嵌套 def 的既有身份局限（同文件同名嵌套 def 因 qn 不含外层函数名而在建图时合并）是**已知建图层边界**，本功能不处理、仅记录在案；跨文件同名函数因 `qualified_name` 内嵌文件路径天然可区分，不受该局限影响。
